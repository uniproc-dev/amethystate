`Store` — тот хендл, из которого всё читают и через который всё пишут. Собирают
его `StoreBuilder`, который решает, куда лягут файлы и какой движок их держит.
`Store` — `Clone`, и клон здесь ещё один хендл на тот же открытый store, а не
второй store.

Обычно приложение открывает один и держит его всю жизнь процесса. Но это не
обязано быть так: открытых store может быть несколько — над разными файлами
или под разными движками.

## По пути, который вы назвали

<!-- shown: opening a store at a path you name -->
```rust
let store = StoreBuilder::new(settings).build()?;
```
<!-- /shown -->

`build` возвращает `Store`. Держите его, передавайте в `new_with`, а на выходе
из процесса дайте дропнуться. Во что это обойдётся, если на результат ни разу
не посмотреть, — см. [Закрытие](#закрытие).

## Или один раз, на весь процесс

Таскать store во всё, чему он нужен, — способ явный, но утомительный. Store на
весь процесс ставят один раз, а достают откуда угодно:

<!-- shown: opening the process-wide store -->
```rust
let _ame = "./app.redb".init_global();

let state = NetworkState::new()?;
```
<!-- /shown -->

`NetworkState::new()` — тот же `new_with`, только глобальный store подставлен
за вас: структура, объявленная где угодно, соберёт себя, не получив на входе
ничего. До самого store тоже можно дотянуться:

<!-- shown: reaching the global store from anywhere -->
```rust
let store = global_store();
store.kv().set("theme", &"dark".to_string())?;
```
<!-- /shown -->

**Guard и есть store.** `init_global` его и возвращает, и стоит на нём
`#[must_use]` по причине грубой: guard дропнули — store закрылся, поэтому
`"./app.redb".init_global();` отдельной строкой открывает store и на той же
строке закрывает. Свяжите его в `main` — `let _ame = ...` — и последние записи
сбросятся, когда `main` вернётся.

Поставить дважды — паника. Внутри `OnceLock`, и второй `init_global` — баг, а
не перенастройка.

Здесь работает та же развилка, что между `build` и `build_with_migration`:

<!-- shown: opening it with the migration pass -->
```rust
let (report, _ame) = StoreBuilder::new("./app.redb").init_global_with_migration();

if report.has_failures() {
    eprintln!("a migration step failed; the data was put back");
}
if report.has_drift() {
    eprintln!("a struct changed without a version bump");
}
```
<!-- /shown -->

## Пусть платформа скажет, где

Написать путь руками — то, что надо для теста или для инструмента, который
направили на конкретный файл. Приложению, которое ставят на чужую машину, нужно
место, отведённое ему платформой, — его и вычисляет `located`:

<!-- shown: letting the platform say where the file goes -->
```rust
let config = StoreBuilder::located(|at| at.app("my-app", "settings"))?;

let named = StoreBuilder::located(|at| at.app_under(Layout::App, "my-app", "settings"))?;

let portable = StoreBuilder::located(|at| at.beside_the_executable("settings"))?;
```
<!-- /shown -->

Предлагают три места:

| как | куда ляжет |
| --- | --- |
| `at.app("my-app", "settings")` | каталог конфигурации, который эта платформа держит для приложения |
| `at.app_under(Layout::App, ..)` | то же самое, но по соглашению, которое вы назвали |
| `at.beside_the_executable("settings")` | рядом с запущенным бинарником — для установки, которую просто распаковали |

### Какому соглашению следует `app`

На вопрос «где приложение держит свои файлы» ответ не один, и `Layout` их
перечисляет:

| layout | куда кладёт файлы |
| --- | --- |
| `Layout::App` | раскладка XDG — на всех платформах, Windows и macOS включительно |
| `Layout::Native` | туда, куда файлы приложения кладёт сама система; вне Linux это уже не XDG |
| `Layout::ProjectDirs` | то, что выдаёт крейт `directories`: XDG на Linux и Windows, `Library/Application Support` на macOS |

`app` выбирает `Layout::App` за вас.

Настольному приложению обычно нужен `Layout::Native` — туда складывает файлы
весь остальной софт платформы, — а `app` его не выберет никогда. Просите по
имени. `Layout::ProjectDirs` берут для приложения, чьи файлы уже лежат там,
куда их кладёт `directories`: store должен попасть туда же, куда смотрит этот
крейт.

**Назовите раскладку, как только выпустили релиз.** Соглашения расходятся по
дереву достаточно, чтобы store, записанный по одному, не нашёлся по другому.
`app_under` как раз и закрепляет, где лежат чьи-то настройки, чтобы обновление
их не потеряло.

### Как переехать, если store уже лежит в другом месте

Кложу зовут один раз, и её ответ — путь. Что она делает до того, как ответить,
решаете вы: `located` отдаёт `Location` и забирает `PathBuf`, а между этим —
обычный код.

Только переезду одного пути мало. Путь — это то, *по чему* store открывают, а
из чего он *состоит*, знает движок: расширение, которое он дописал, спутник
рядом, копия, которую он держит, пока переписывает файл. Раскладка называет их
все, и переезд — перебор по ней:

<!-- shown: moving every file a store is made of -->
```rust
fn relocate(from: &StoreLayout, to: &StoreLayout) -> std::io::Result<()> {
    for (old, new) in from.names().iter().zip(to.names()) {
        if old.exists() {
            std::fs::rename(old, new)?;
        }
    }

    Ok(())
}
```
<!-- /shown -->

**`names` — это все имена, а не все файлы.** Копию на время переписывания заводят
в начале и убирают в конце, так что у store, который лежит себе спокойно, её нет,
— потому переезд выше и пропускает то, чего нет, а не спотыкается об это. Две
раскладки одного движка сходятся имя к имени: файл с данными ляжет файлом с
данными, спутник — спутником. `present` — тот же список, только без пропавших:
им спрашивают, что на диске есть на самом деле.

Саму раскладку по пути — не открывая ничего — отдаёт `at.files_at`, и старое
место как раз тем и неудобно, что спросить у него некого:

<!-- shown: a store found where an older release left it -->
```rust
let store = StoreBuilder::located(|at| {
    let now = at.app(&app, "settings")?;
    let was = at.files_at(at.app(&app, "settings-legacy")?, backend);

    relocate(&was, &at.files_at(&now, backend)).ok();

    Ok(now)
})?
.backend(backend)
.build()?;
```
<!-- /shown -->

Вот и весь ответ на «выпустили под одной раскладкой, хотим другую». Ничего
особенного тут нет: перенесите файлы, скопируйте, спросите сперва человека или
откройте старое место и оставьте как есть — библиотека не делает ничего из
этого и ничего из этого не запрещает. Ей отдают один путь, остальное она
соберёт сама.

Сойдётся ли переезд — тоже ваше. Кложа, которая продолжает отвечать старым
путём, оставляет оба места жить вечно. Но это решение, а не недосмотр: оно
написано там, где его видно.

`beside_the_executable` — для переносимой установки, а не для той, которую
ставят: в `Program Files` и `/usr/bin` тому, кто запускает программу, писать
не дадут, а на macOS бинарник сидит внутри подписанного бандла. Любое из этого
вылезет наружу отказом открыть store — при запуске, то есть в самый подходящий
момент.

## Каким файлом становится имя

Если у пути, который вы дали, нет расширения, файл называет движок:

<!-- shown: letting the engine name the file -->
```rust
let store = StoreBuilder::new(config_dir.join("settings"))
    .backend(Backend::Json)
    .build()?;
```
<!-- /shown -->

Так получается `settings.json`. Назовите расширение сами — его не тронут:

<!-- shown: naming the file yourself -->
```rust
let store = StoreBuilder::new(config_dir.join("settings.conf"))
    .backend(Backend::Json)
    .build()?;
```
<!-- /shown -->

Получается `settings.conf`, внутри всё тот же JSON. Правило тут про владение, а
не про формат: имя, написанное вами, — ваше, и `.conf`, за которым уже следит
другой инструмент, продолжит работать; имя, придуманное библиотекой,
принадлежит тому движку, который в итоге работает. Заметнее всего это, когда
`backend` зовут уже после того, как задан путь: расширение в этот момент
выводят заново.

Какие движки есть и что каждый пишет:
[Установка](/amethystate/ru/getting-started/installation/).

## Что делать, если значение не читается или ключ исчез

Два решения, и без них не открыться: на диске лежит то, что не разбирается в
объявленный тип, — падать или брать дефолтное значение? Ключ под полем удалили —
показывать последнее, что было, или сбрасываться до дефолтного?

По умолчанию открытие отказывает, называя путь, а поле с удалённым ключом
продолжает показывать значение, которое держало до удаления. Сказать иначе —
здесь:

```rust
use amethystate::store::OnUnreadable;

let store = StoreBuilder::new(path)
    .rules(|r| r.on_unreadable(OnUnreadable::UseDefault))
    .build()?;
```

Одно и то же правило пишут в трёх местах: здесь, на store; атрибутом на
структуре; атрибутом на отдельном поле. Побеждает то, что ближе к данным, —
значит, сказанное здесь слабее двух других. `Refuse`, написанный на структуре,
останется `Refuse`, что бы ни сказали store: отсюда чужое обещание не отменить,
отсюда его только выдают тем, кто ничего не обещал.

Этим он и безопасен. Скажем, приложение держит в store сгенерированные
миниатюры, а рядом — лицензию. Ни одна миниатюра не стоит того, чтобы не
запуститься, а лицензия стоит:

<!-- shown: one process, two answers about the same store -->
```rust
#[amethystate(prefix = "thumbnails")]
pub struct Thumbnails {
    #[amestate(default = 0u32)]
    pub generated: u32,
}

#[amethystate(prefix = "licence", on_unreadable = Refuse)]
pub struct Licence {
    #[amestate(default = "".to_string())]
    pub holder: String,
}
```
<!-- /shown -->

Открытый с `UseDefault`, нечитаемый счётчик миниатюр заменяется объявленным
значением, и приложение стартует. Нечитаемая лицензия его всё равно остановит —
`Licence` сказала это про себя. Один store, один процесс, и решает та структура,
которой было не всё равно.

Без этого значение, которое не декодируется, откажет в открытии, а поле с
удалённым ключом продолжит показывать последнее, что держало. Что из этого что
и почему: [Объявление структур](/amethystate/ru/state/defining-structs/).

## Какие миграции выполняются

`build` прогоняет те шаги, которые передали билдеру, и никакие другие.
`build_with_migration` вдобавок собирает все `#[migrate]` из бинарника и
возвращает вместе со store отчёт о том, что проход сделал.

Поэтому store, открытый через `build` в бинарнике, полном `#[migrate]`, не
мигрирует ничего и ни слова об этом не скажет. Раз в деле макрос — берите
`build_with_migration`. [Миграции](/amethystate/ru/migrations/overview/).

## Сброс буфера на диск

Дроп store сбрасывает то, что тот держал, поэтому при обычном выходе ничего не
пропадает. Только вот лёг ли сброс, дроп не скажет, — а диск, который в этот
момент оказался полон, узнать хочется:

<!-- shown: writing the buffer out and hearing whether it landed -->
```rust
store.kv().set("port", &8080u16)?;

if let Err(report) = store.save_now() {
    eprintln!("settings were not saved: {report:?}");
}
```
<!-- /shown -->

`save_now` — тот же сброс, только ошибку он отдаёт вам. Store после этого
работает дальше: дроп, когда до него дойдёт, сбросит ещё раз, а о том, что
найдёт, доложит в лог, а не вам. В этом и вся разница — дропа никто не
слышит.

## Закрытие

После `save_now` store продолжает держать свой файл. `close` его отдаёт: пишет
то, что в буфере, останавливает фоновый поток и отпускает.

<!-- shown: closing the store and letting go of the file -->
```rust
if let Err(report) = store.close() {
    eprintln!("the last writes were not saved: {report:?}");
}
```
<!-- /shown -->

Дальше любое чтение, запись, скан и сброс в этот store отвечают `Closed` —
`ReadValue::Closed`, `WriteValue::Closed`, `ScanKeys::Closed`, `Flush::Closed`,
и каждый называет то место, о котором спрашивали, — и каждый его клон тоже,
файл у них один на всех. Позвать дважды можно, ничего не случится, и дроп
следом тоже ничего не сделает.

Поле — исключение, и нарочно: `get` оно отвечает из памяти дальше, а говорит об
этом через `try_get`, у которого `Reason::Closed` значит «это последнее, что я
слышало», а не «это упало».

Зовут его тогда, когда файл понадобился кому-то ещё: другому процессу,
резервной копии, переименованию. Что именно это даст, зависит от движка —
каждый отдаёт то, что держал:

| движок | что занимает живой store | что освобождает закрытие |
| --- | --- | --- |
| sqlite | файл, против всей машины | переименование и удаление начинают работать |
| redb | право его открыть | второй store сможет открыть тот же путь |
| json, toml, ron | ничего между сбросами | только фоновый поток |

Поле продолжает отвечать на `get` из памяти, так что построенное по последним
значениям никуда не денется. Видно закрытие на
[`try_get`](/amethystate/ru/concepts/errors/): он скажет, что store закрыт, а
то, что держит поле, — последнее, что полю успели сообщить.

**Глобальный store закрывается так же.** Его закрывает дроп guard, а ошибка
уходит в `tracing::error!` под таргетом `amethystate` — туда, где вызывающий с
ней уже ничего не сделает. Ошибку отдаёт обратно `amethystate::shutdown()`, и
зовут его до того, как guard выйдет из области видимости. Статик не дропается
никогда, поэтому без одного из двух последний интервал дебаунса пропадёт даже
при чистом возврате.

Даёт это ровно одно: вы узнаёте о провале и можете сказать о нём человеку.
Спасти записи на этом месте уже нельзя — store закрыт, и всё, кроме `get` из
памяти, отвечает `Closed`. Повторный `close` тоже не поможет: он видит, что
закрытие уже началось, и отвечает `Ok`, ничего не сбрасывая. Место для второй
попытки — `save_now`, пока store ещё открыт.

Как дождаться диска ради одной записи, а не всех сразу:
[Durability](/amethystate/ru/concepts/durability/).
